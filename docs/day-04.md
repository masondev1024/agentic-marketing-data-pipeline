# 실습 4 — 고정된 개발 평가와 실패 분류

## 왜 평가를 먼저 만드는가

한 질문을 바꾸면서 답변이 좋아지는지 보는 것만으로는 개선을 판단하기 어렵다.
다른 질문이 나빠졌거나, 문서가 바뀌었거나, 출력이 길어져 좋아 보일 수도 있다.
같은 질문·문서·채점 기준을 고정하고 검색과 생성을 따로 관찰한다.

이번 범위는 개발용 20문항과 실행기다. 잠금 테스트셋, 모델 비교, API 운영 평가는 이후 단계다.
개발셋에는 이미 실험했던 질문이 포함되어 있다. 20문항 결과를 일반적인 서비스 정확도로 부르지 않는다.

## 데이터 계약과 채점

`data/eval/development-v1.jsonl`은 멱등성 5개, 재시도 5개, 백필 5개,
범위 밖 질문 5개다. 각 행의 계약은 다음과 같다.

| 필드 | 의미 |
|---|---|
| id | 중복 없는 고정 문항 ID |
| question | 모델에 전달할 실제 질문 |
| expected_source | 기대하는 문서 파일명. null이면 생성 전 보류 기대 |
| must_include | 사람이 의미를 확인할 필수 내용 |
| must_not_claim | 사람이 확인할 금지 주장·단위 혼동·근거 없는 사실 |

빈 질문, 중복 ID, 알 수 없는 필드, 없는 정답 문서 등은 모델 호출 전에 거절한다.
최대 100문항·256 KiB로 제한한다. 질문이나 기준을 수정하면 SHA-256이 달라진다.
큰 의미 변경은 v2 파일을 만들어 이전 기준도 보존한다.

문서에 관련 주제는 있지만 특정 값이 없는 질문도 있다. 예를 들어 첫 재시도 간격의 정확한
초 값은 문서에 없다. 이 문항은 retry.md를 선택한 다음 '문서에 값이 없다'고 답해야 한다.
실제 회사 백필의 실행 ID처럼 회사 기록 자체가 없는 질문은 검색 단계 보류가 목표다.
현재 검색기는 이러한 구분에 실패할 수 있다. 평가에 맞춰 정답 라벨을 바꾸지 않는다.

## 실행

프로젝트 폴더에서 먼저 모델 없이 검색만 확인한다.

```sh
uv run --locked python -m llm_ops_lab.evaluation --search-only
```

이어서 캐시된 모델로 같은 질문을 실행한다.

```sh
uv run --locked python -m llm_ops_lab.evaluation --offline \
  --temperature 0 --max-tokens 256 --seed 42
```

기본 operator는 learner다. assistant가 환경을 검증할 때는 `--operator assistant`를 붙인다.
새 의존성이나 별도 API Key는 필요 없다. 문항별 제한 시간은 120초이며
`--timeout-seconds`로 1~600초 사이에서 설정한다.

## 결과 읽기

매번 `runs/evaluations/<새 UUID>/`를 만든다. 이전 결과는 덮어쓰지 않는다.

- `manifest.json`: 질문 파일·문서·소스 코드·lockfile 해시, 모델 revision, 조건, 실행자.
  model_id/revision은 계획한 모델이다. 실제 실행 여부는 각 추론 JSON에서 확인한다.
- `dataset.jsonl`, `corpus/`: 이 배치에 사용한 입력 사본.
- `cases/<id>/<run_id>.json`: 기존 CLI의 원본 추론 기록. 실제 프롬프트와 근거도 포함한다.
- `cases/<id>/result.json`, `stdout.log`, `stderr.log`: 문항 결과, 오류와 로그.
- `summary.json`: 전체 실행이 끝난 뒤 기록하는 집계와 문항 결과.
- `review.md`: 필수 내용·금지 주장·관측 답변을 모아 둔 수동 채점표.

자동 지표는 '문서 선택 또는 보류가 기대와 일치한 개수 / 전체 문항 수'다.
정답 문서가 있는 15문항과 보류 기대 5문항도 분리한다. 실행 오류는 분모에서 빼지 않는다.
behavior_pass는 generated/abstained/search_only와 모델 실행 여부에 대한 경로 검사다.
이 값과 retrieval_pass는 정답·근거 충실성 점수가 아니다.

실행기 종료 코드 0은 배치를 오류 없이 수집했다는 뜻이다. 품질 합격을 뜻하지 않는다.
실행 오류가 하나라도 있으면 요약은 completed_with_errors, 종료 코드는 1이다.
검색 실패를 코드 오류로 간주해 숨기거나 재시도로 덮지 않는다.

## 사람의 답변 평가

생성 배치의 review.md에서 각 답변을 아래 기준으로 검토하고 판정 근거를 적는다.
검색만 실행한 배치는 답변 평가 대상이 아니다.

1. 사실/필수 내용: must_include의 의미를 모두 충족하는가?
2. 근거 충실성: 금지 주장이 없고, 문서에 없는 수치나 사실을 지어내지 않는가?
3. 형식: 생성 답변이 제목·목록 없이 정확히 두 문장인가?

각 항목을 pass/fail로 기록한다. 범위 밖 질문은 올바른 보류인지 판단하고 형식은 N/A다.
실행 오류는 '오류', 검색 실패로 필요한 답을 못 한 경우는 실패로 남긴다.
미검토는 통과로 집계하지 않는다. 이번 실행기는 수동 판정을 자동 합산하지 않는다.
'5회', 'backoff' 같은 단어가 있다는 이유만으로 정답으로 처리하지 않는다.

먼저 retry-policy의 간격/횟수 구분과 unknown-private-backfill의 실제 회사 기록 여부를
직접 판단해 보자. assistant의 검토는 별도 증거이며 본인의 검토로 바꿔 기록하지 않는다.

## 변경 전후 비교

두 배치의 manifest에서 dataset_sha256, corpus_sha256, settings, model revision,
source_sha256을 확인한다. 바꾼 요인 하나 외에는 동일해야 해석하기 쉽다.
예: 문서와 평가셋, 모델, 생성 조건을 유지하고 context.py의 프롬프트만 바꾼다.
각 배치의 같은 case_id를 대조하여 개선·퇴행 사례를 모두 기록한다.
source_sha256은 실제 변경 여부를 확인하기 위한 것이며, 모든 코드 변경이 품질 변화 원인은 아니다.

동일한 문서도 UUID 경로를 프롬프트에 넣으면 입력이 달라진다. 이를 피하려고
자식 CLI의 작업 디렉터리를 배치로 설정하고 항상 `corpus/<파일명>`을 전달한다.
문항 실행 중 코드 또는 사용 문서 해시가 달라지면 해당 문항을 오류로 처리한다.

## 실패·복구·비용상의 선택

단일 프로세스에 모델을 공유하면 로딩 비용이 줄지만, 이번에는 문항별 자식 프로세스를 사용한다.
기존 CLI를 그대로 검증하고 시간 초과 시 프로세스를 종료하며 문항 간 모델 상태를 분리하기 위해서다.
대신 모델을 매번 로딩하므로 전체 배치 시간은 서비스 요청 지연이나 처리량 벤치마크가 아니다.
병렬 생성은 하지 않는다. 문항별 로그와 결과를 즉시 저장하고 오류 뒤에도 다음 문항을 실행한다.

배치 도중 중단되면 manifest와 완료된 문항 결과가 남고 summary가 없을 수 있다.
summary가 없는 폴더는 완료로 취급하지 않는다. 같은 명령을 재실행하면 새 배치를 만들며,
이번 버전은 자동 이어하기나 기존 결과 합치기를 하지 않는다.
문서 사본은 읽은 내용 기준으로 고정하지만, 복사 시작 시 여러 원본 파일의 원자적 스냅샷을
보장하지는 않는다. 배치 준비 중에는 원문을 수정하지 않는다.

실제 대규모 평가에서는 작업 큐, 재개 가능한 체크포인트, 모델 워커 재사용과 자원 제한이 필요하다.
지금은 20문항에서 오류를 보존하고 조건을 추적하는 경로부터 검증한다.
