# 근거 선택·답변 생성 분리 — 실험 기능으로 유지

2026-10-07 KST에 오늘 작업을 마무리했다. `day-10`은 학습 단계 번호이며 운영 일수가 아니다.
`--answer-mode evidence-v1`을 구현하고 실제 40문항 평가를 완료했다.
기본값은 기존 `direct`다. API 구축과 운영 검증은 다음 작업으로 남겼다.

## 무엇이 달라졌나

문서 검색 → 원문 스냅샷과 문장 ID 생성 → 모델이 근거 ID 선택 → 선택 검증 →
선택된 문장만 전달해 답변 생성 → JSON/인용 ID/원문 위치 검증 → 답변과 인용 출력 순서다.

원문 인용은 모델이 새로 쓰지 않고 코드가 ID에 해당하는 원문 구간에서 가져온다.
문서 SHA-256과 문자 오프셋을 검증하므로 인용문이 원문에 있는지 확인할 수 있다.
**인용문이 실제 존재해도 답변이 그 문장의 의미를 정확히 설명한다는 보장은 없다.**
선택 단계가 필수 조건을 빠뜨리면 생성 단계는 그 조건을 볼 수 없다는 새로운 실패 경로도 있다.

`evidence.py`가 스냅샷·출력 계약·단계 진행을 담당하고, `cli.py`가 모델 로딩과 추론·저장을 담당한다.
평가 실행기는 모드를 전달하고 코드/문서/모델/설정의 출처를 검증한다.
모델은 한 번 로드한 뒤 최대 두 번 순차 호출한다. 자동 재시도나 다른 모드로의 자동 전환은 없다.

## 실패와 복구

- 검색 보류: 모델을 호출하지 않는다.
- 빈 근거 선택: 답변 생성을 호출하지 않고 보류한다.
- 잘못된 JSON, 중복/미등록/선택 범위 밖 ID, 출력 잘림: `evidence_rejected`로 게시를 차단한다.
- 단계 실행 오류: `pipeline_error`와 앞 단계 기록을 저장하고 실패 종료한다.
- 완료 단계는 `.stages.jsonl`에 flush/fsync한다. 평가기도 실패 기록과 저널 경로를 보존한다.

재실행은 새 UUID를 사용해 이전 결과를 덮어쓰지 않는다. 저널은 완료 단계의 진단 증거이며
자동 재개 기능은 아니다. 강제 종료 시 진행 중인 생성 토큰까지 모두 복구한다고 보장하지 않는다.
문장 분리는 구두점 기반 휴리스틱이고 최대 128개, 선택은 최대 6개다.
선택 출력은 128토큰, 답변 출력은 지정한 `--max-tokens`, 단계별 입력은 최대 2,048토큰이다.

## 실제 결과

Qwen3-4B 4bit 고정 revision, `scoped-v3`, `baseline`, temperature 0, seed 42,
답변 최대 256토큰으로 기존 개발 20문항과 추가 검증 20문항을 순차 실행했다.
코드·lockfile·문서·scope·평가셋을 실행 전에 고정했고 완료 후 해시 일치를 확인했다.
모든 실행과 수동 채점은 assistant가 수행했다. 학습자의 직접 실행 완료로 기록하지 않는다.

| 항목 | 결과 |
|---|---:|
| 검색 선택/보류 일치 | 40/40 |
| 범위 밖 질문의 모델 실행 전 보류 | 15/15 |
| 답변 대상 | 25 |
| 최종 답변 출력 | 21 |
| 잘못된 JSON으로 답변 차단 | 3 |
| 빈 근거 선택으로 보류 | 1 |
| 필수 내용·근거 동시 충족, 보류/차단 포함 | **13/25** |
| 출력 답변의 원문 인용 일치 | 21/21 |
| 출력 답변의 두 문장 형식, 수동 확인 | 21/21 |
| 출력 답변의 한국어 사용 | 20/21 |
| 실행 오류 / 토큰 한도 도달 | 0 / 0 |

3개의 JSON 실패는 제어된 답변 차단이므로 프로세스 실행 오류 0과 구분한다.
두 문장 형식은 코드상 JSON 항목 두 개 검증과 별도로 실제 출력을 읽어 확인했다.
원문 일치 분모 21과 의미 정확성 분모 25를 혼용하면 성능을 과장하게 된다.

개발셋 내용 통과는 8/15, 추가 검증셋은 5/10이다. 이전 direct baseline 결과는 18/25였다.
이전 배치와 질문·루브릭·문서·scope·모델·생성 설정의 일치를 확인했지만, 이번에 direct 전체를
동시에 재실행한 비교는 아니다. 생성 구조와 실제 메시지 전체가 달라졌으며 개별 지시의 효과를
분리한 실험도 아니다. 정확도 개선 기능으로 채택하지 않고 오류 추적용 실험 모드로 유지한다.

### 실패가 알려 주는 것

| 사례 | 관측된 문제 | 실패 위치 |
|---|---|---|
| retry-policy | backoff/jitter 문장을 선택하지 않아 간격 정책 누락 | 근거 선택 |
| backfill-concurrency | 저장소 트랜잭션/스냅샷 조건 누락, 출력 JSON도 잘못됨 | 선택과 생성 계약 |
| idempotency-recovery | 재시도를 허용하는 근거를 보고도 “재시도를 금지해야 한다” 출력 | 의미 해석 |
| time-seconds | 초 값이 없는 원문을 인용하며 “1초로 명시”라고 날조 | 의미 해석 |
| retry-timeout, backfill-recovery | JSON 뒤 따옴표, 답변 항목도 한 개 | 생성 계약 |
| team-checkpoint-design | 핵심 내용은 있지만 한국어·중국어·영어가 섞임 | 언어 품질 |

backfill-prepare의 “보장하기 위해”는 목적 설명으로, time-minutes의 모호한 둘째 문장은
고정 수치 부재라는 질문 범위로 관용적으로 통과시켰다. 엄격한 평가에서는 점수가 더 낮아질 수 있다.
평가 문항은 이미 개발에 사용됐고 assistant 수동 채점이므로 독립 테스트나 사람 합의 점수가 아니다.
평가 결과를 본 뒤 프롬프트를 추가 조정하거나 실패 사례를 분모에서 빼지 않았다.

## 검증과 비용

테스트 **195개**, Ruff 통과. 잘못된 스키마/ID, 원문 변조, 빈 선택, 단계별 잘림,
2단계 실행 실패, 실패 기록 보존, 타임아웃 저널, 검색 보류 시 모델 미호출을 검사했다.
독립 코드·아키텍처 리뷰의 오류 기록 누락 지적을 수정한 뒤 실제 평가를 실행했다.
구조 검증을 통과한 잘못된 인과 답변도 테스트에 포함해 의미 검증과의 경계를 드러냈다.

실제 기록에서 인용 위치·해시, 선택 문장만 전달됐는지, 질문 보존, 저널과 단계별 토큰 합계를 검증했다.
기존 사용자 질문을 direct로 한 번 재실행해 이전 메시지·입력 토큰 해시·출력과 동일함도 확인했다.
이는 한 질문의 호환성 확인이며 전체 direct 회귀 평가나 그 답변의 정확성 증명은 아니다.

모델을 실행한 25문항에서 총 49회 호출했다. 입력 토큰 합계 중앙값 1,063,
출력 토큰 합계 중앙값 93, 두 단계 생성 시간 합계 중앙값 8.02초,
MLX 최대 메모리 3.10GB였다. 선택 25회의 생성 중앙값은 3.71초, 답변 24회는 4.23초다.
차단/보류 사례도 포함한 로컬 순차 실행 관측값이며 서비스 응답시간·동시성·p95가 아니다.

## 재현

프로젝트 루트에서 다음 명령으로 실험 모드를 확인할 수 있다. 오늘 추가 실행할 필요는 없다.

```sh
uv run --locked llm-lab --offline --model qwen3-4b \
  --corpus-dir data/runbooks --retriever scoped-v3 \
  --answer-mode evidence-v1 --prompt-variant baseline \
  --temperature 0 --max-tokens 256 --seed 42 \
  --prompt '우리 팀에서 재시도 횟수를 제한해야 하는 이유는?'
```

`--answer-mode direct`로 기존 경로를 사용한다. 다른 경로 이름도 모델 메시지에 포함되므로
CLI와 평가기에서 질문이 같다고 출력이 반드시 같지는 않다.

```sh
uv run --locked python -m llm_ops_lab.evaluation --offline \
  --model qwen3-4b --retriever scoped-v3 --answer-mode evidence-v1 \
  --prompt-variant baseline --temperature 0 --max-tokens 256 --seed 42
```

추가 검증은 `--dataset data/eval/retrieval-challenge-v1.jsonl`을 붙인다.
배치 `459b11a5-d8d3-4356-9857-a2fa91699dc3`, `d2f64469-881d-4289-bdf9-93565f5fc6af`의
원본 자동 요약은 유지하고 `review.assistant.json/md`를 별도로 저장했다.

## 다음 작업 — 로컬 LLM API

사용자 요청에 따라 오늘 범위는 여기서 종료한다. 내일은 추가 프롬프트 실험을 먼저 늘리지 않고
기존 추론 경로를 API로 연결한다. 공개 배포·학습·인증 구축까지 완료했다는 의미가 아니다.

1. 요청/응답 계약: 질문, 답변, 출처, 보류/실패 사유, request ID를 정의한다.
2. 수명주기: 모델을 프로세스 시작 시 한 번 로드하고 liveness와 readiness를 구분한다.
3. 자원 보호: 우선 한 번에 한 추론, 제한된 대기열, 입력/토큰 한도, 명시적인 과부하 응답을 설계한다.
4. 타임아웃·복구: HTTP 시간 초과 뒤에도 GPU 작업이 계속될 수 있으므로 취소/worker 복구 경계를 검증한다.
5. 관측·실행 검증: 검색/생성/대기 시간과 상태를 기록하고 정상·보류·잘못된 입력·동시 요청·재시작을 확인한다.

완료 기준은 로컬 HTTP 요청으로 답변/출처/보류를 확인하고, 실패 및 과부하 경로를 재현하는 것이다.
초기 서버는 loopback에 바인딩한다. 공개 배포와 GitHub 게시에는 별도 승인과 준비가 필요하다.
현재 의미 품질 한계도 API 응답의 검증 상태와 문서에 명시한다.
