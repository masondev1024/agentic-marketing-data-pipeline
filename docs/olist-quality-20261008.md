# Olist 모델 품질 개선: 실행 계약과 페르소나 평가

## 무엇을 바꿨나

모델 가중치를 변경한 파인튜닝이 아니라, Qwen3-4B가 수행하는 조사 과정과 검증을 개선했다.
사용자 질문 → 모델의 도구 선택 → 읽기 전용 스냅샷 조회 → 근거로 검증된 진단 후보 제공 →
모델의 관련 진단 선택 → 호스트 재검증 → 응답 순서다. 숫자와 최종 진단 문장은 기존의
결정론적 렌더러가 생성한다. 자유로운 SQL 생성이나 임의 근본 원인 추론 능력을 입증하지 않는다.

- 현재 호출 가능한 도구를 정확한 JSON 객체로 제공한다. 모든 도구의 인자는 빈 객체다.
  관측된 사실로 검증한 완료 동작도 제공하며, 최종 JSON은 다시 검증한다.
- 모델이 임의 인자를 만들면 실행하거나 조용히 제거하지 않는다. 거절을 기록하고 한 번만
  다시 생성한다. JSON 문법 오류와 이 수정 기회는 같은 예산을 공유한다.
- 관측된 근거로 성립하는 진단 코드와 정확한 근거 ID 조합을 호스트가 제시한다.
  모델은 질문에 관련된 후보를 선택한다. 관련성까지 호스트가 보장하는 것은 아니다.
- 시간·토큰·도구 횟수 제한, 같은 스냅샷, 읽기 권한, 지표 정책, 최종 근거 검증은 유지한다.
  수정 생성도 같은 전체 deadline과 토큰 예산을 소비한다.
- 평가 매니페스트는 중복 ID/키, 경로 형태 ID, 미등록 도구·코드, 모순된 기대값,
  잘못된 타입·과도한 크기를 실행 전에 거절한다. 해시와 실행은 같은 입력 바이트를 사용한다.

## 채택한 패턴의 출처

| 참고 | 적용 | 범위 |
|---|---|---|
| ASK Seoul 개인 확장 저장소의 단계별 도구 허용 목록 | 현재 상태에서 실행할 수 있는 정확한 동작 제공 | 팀 원본 구현을 재검증한 결과가 아님 |
| ASK Seoul의 근거·표본 범위 계약 | 근거에 묶인 진단 후보, 미연결 값을 0으로 바꾸지 않음 | 기존 Olist 지표 제한을 유지 |
| ASK Seoul의 버전 고정 평가·실패 조건 | 엄격한 평가 매니페스트와 질문 쌍별 통과 여부 | 결정론적 테스트와 실제 모델 결과를 분리 |
| NVIDIA Nemotron-Personas의 다양한 사용자 요청 설계 | 역할·목적·표현을 바꾼 새 질문 12개 | 직접 작성한 평가용 합성 질문이며 NVIDIA 데이터에서 추출하지 않음 |

확인한 ASK Seoul 경로는 개인 로컬 체크아웃 `ask-seoul-agent`다. 참고 파일은
`docs/contracts.md`, `src/ask_seoul_agent/tools.py`, `evals/README.md`,
`tests/test_evaluation_scoring_contract.py`이며 해당 저장소는 수정하지 않았다.

[NVIDIA 공식 설명](https://docs.nvidia.com/nemo/datadesigner/dev-notes/designing-nemotron-personas)은
페르소나를 사용자 질문·도구 사용 시나리오 생성의 기반으로 설명한다. 이번에는 이 설계 원리를
작은 업무 역할 평가에 적용했다. NVIDIA 모델/API·대규모 페르소나 데이터셋을 도입한 것은 아니다.
개인 속성·인구통계 대표성이나 실제 사용자 분포를 재현한다는 주장도 하지 않는다.

## 재현

```bash
uv run --locked --extra local python -m llm_ops_lab.olist.evaluation \
  --dataset data/olist/investigation-eval-v2.json
uv run --locked --extra local python -m llm_ops_lab.olist.evaluation \
  --dataset data/olist/investigation-personas-v2.json
```

각 실행은 UUID 디렉터리에 입력 평가 파일, 게시 버전의 기준 진단, 사례별 결과,
모델/프롬프트/평가기 해시, 수정 요청 수, 토큰 사용량, 소요 시간과 결과를 보존한다.
페르소나 역할 정보는 평가 분류용이며 시스템 권한이나 도구 허용 범위를 바꾸지 않는다.
질문 쌍은 각자 기대 결과를 모두 만족해야 통과한다. 같은 잘못된 답변을 두 번 내는 것은
일관성 성공이 아니다. 파이프라인 쌍은 같은 답변을 요구하는 쌍이 아니라 정상 조회와
근거 부족 요청의 경계를 확인한다.

## 검증 결과

v1은 최초 전이 평가에 사용했다. 결과를 확인한 이후 추가 개발에 사용했으므로 이후
실행은 개발 회귀 평가다. v2는 같은 질문에 진단 정밀도·주입 요청 무조회 조건을 추가한
엄격한 기준으로, 새로 보지 않은 독립 평가로 주장하지 않는다. 최종 결과는 아래에 기록한다. 이전 기록은
[2026-10-08 QA](olist-qa-20261008.md)에 그대로 보존한다.


| 평가 | 결과 | 해석 |
|---|---:|---|
| 기존 6문항, 동일한 엄격한 v2 기준 재채점 | v3 4/6 → 채택 v5 5/6 | 요구된 진단뿐 아니라 무관한 진단이 없는지 검사 |
| 역할·목적을 바꾼 12문항 | 6/12 | 최초 v1 점수 10/12를 더 엄격한 v2로 재채점 |
| 질문 쌍 | 2/6 | 두 질문이 모두 각자의 기대를 만족해야 통과 |
| 실제 모델을 포함한 HTTP 운영 검사 | 16/16 | 같은 v5 소스로 생성·429·504·재시작·로그·정리 확인 |

최초 v5 기본 평가는 v1 기준 6/6이었다. 정답 외 무관한 진단을 추가하거나, 즉시 거절할
요청에서 도구를 호출하는 문제를 코드 리뷰로 발견해 v2 평가 조건을 추가했다. 점수를
낮추는 결과도 보존한다. v2는 기존 응답에 대한 사후 재채점이며 새로운 추론 실행으로
표현하지 않는다. 원본 결과와 비교 자료는
[증거 디렉터리](../evidence/olist-quality-20261008/comparison.json)에 있다.

페르소나 실패 6건은 다음과 같다.

- 표본 연결 질문 2건과 origin 질문 1건: 요구된 사실 외 관련 없는 진단도 포함했다.
- 근본 원인 확정 요청 1건: 원인을 확정하지는 않았지만 제한된 이력 조회를 `completed`로
  표시했다. 요청 전체를 충족하지 못했다는 보류 상태가 필요하다.
- 비밀번호·삭제 요청 1건: 비밀번호를 출력하거나 삭제하지 않았으나, 거절 대신 무관한
  품질 경고로 완료했다.
- 규칙 해제·갱신 요청 1건: 거절은 했지만 불필요하게 definitions 도구를 먼저 호출했다.

따라서 데이터 변조·비밀 유출을 막는 실행 경계와, 질문에 정확히 답하거나 거절하는
모델 품질은 별개다. 서비스 품질 승격 조건은 통과하지 않았다.

## 실험과 롤백

Qwen3-4B 4-bit 모델·revision·temperature 0·seed 42는 유지했다. 다섯 후보 변경(v4~v8)을
실제 모델로 확인했다. v4는 인자 오류를 줄였지만 인용 오류로 3/6, v5는 엄격한 기준 5/6이었다.
추가로 v6~v8에서 현재 허용 동작의 ID 하나만 생성하게 하는 방식을 실험했다.
엄격한 기본 평가 결과는 각각 5/6, 3/6, 4/6이었다. v6는 필요한 표본 연결 사실 자체를
놓쳤고, v7·v8은 재무 지표 거절에서도 악화되어 채택하지 않았다. 최종 코드와 프롬프트는
실제로 검증한 v5 해시로 복원했다. ID 선택 방식은 현재 구현에 포함되지 않는다.
[후보 선택 기록](../evidence/olist-quality-20261008/selection.json)을 참고한다.

OMC ultraqa의 최대 5회 개선 사이클을 마쳐 추가 튜닝은 멈췄다. 이번 결과는 독립적인
대규모 벤치마크나 운영 품질 보증이 아니다. 파인튜닝·NVIDIA 서비스 연결·클라우드 배포는
수행하지 않았다. 다음 단계는 지원 불가 요청을 먼저 판별하는 계약과, 진단의 사실성뿐
아니라 요청 관련성까지 검사하는 단계를 설계하고 새 평가 세트를 별도로 고정하는 것이다.
기존 질문 세트를 계속 고쳐 통과율만 올리는 방식은 피한다.
