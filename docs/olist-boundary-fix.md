# 근거 부족과 위험 요청의 분류 오류 수정

2026-10-08. NVIDIA Super를 사용하는 제한된 요청 분류 후보의 정확성 오류를 수정했다.
최종 후보는 회귀 24문항·새 16문항·거절 반복 24회에서 **64/64**, 기존 실패 질문만의
반복 검사에서 **10/10**을 통과했다. 이를 모든 질문의 정확성이나 HTTP 배포 완료로 해석하지 않는다.

## 문제와 수정

이전 독립 평가에서 외부 운영 로그와 배포 기록으로 장애 원인을 입증하라는 읽기 요청이
`unsafe`로 분류됐다. 올바른 사유는 근거가 없어 확인할 수 없다는 `unavailable_root_cause`다.
잘못된 분류도 조회 없이 보류됐으므로 위험한 실행은 없었지만, 거절 이유가 부정확했다.

수정 전 재현에서는 10회 중 4회 오류가 났다. 출력에는 이미 근거 부족 라벨이 있었지만
`unsafe`가 추가됐고, 호스트의 정상적인 안전 우선순위 때문에 최종 사유가 바뀌었다.
첫 문구 보강 후보 v6는 10회 모두 같은 오류가 나 채택하지 않았다. 실패 결과를 보존했다.
이 기록만으로 모델 내부에서 왜 해당 단어를 위험하다고 판단했는지는 확정할 수 없다.

채택한 `olist-intent.v7`은 분류 지침을 짧은 영어 구조로 다시 정리하고, `unsafe`를
추가하기 전에 실제로 요구된 금지 행위를 확인하도록 했다. 자격 증명 공개·쓰기·삭제·우회가
없는 읽기 요청은 도구가 없다는 이유만으로 위험 요청이 되지 않는다. “확인할 수 없으면
답변을 중단”하는 조건도 시스템 종료나 규칙 해제로 취급하지 않는다.
특정 질문 문자열 예외나 정답 라벨 교체를 넣지 않았고 호스트의 안전 우선순위도 유지했다.
언어 변경 하나만의 효과를 분리 측정한 실험은 아니다.

## 동결한 후보의 실측

| 검사 | 결과 | 해석 |
|---|---:|---|
| 과거 실패 질문 반복 | 10/10 | 개발에 사용한 질문의 재현 확인 |
| 과거 독립 평가 24문항 | 24/24 | 이번 수정에서는 회귀 세트 |
| 별도 작성한 새 경계 문항 | 16/16 | 후보 결과를 보기 전에 기대값·질문 고정 |
| 주요 거절 12문항 × 두 새 프로세스 | 24/24 | 지원 불가·원인·위험 요청의 반복 검사 |

새 16문항은 별도 작성자가 지원 4, 읽기 전용 근거 부족 4, 위험 요청 4,
금융·범위 밖 4문항으로 만들었다. 기존 질문과 정규화 exact 중복은 없지만,
동일한 공개 합성 페르소나 풀과 제한된 업무를 사용했으므로 모집단 독립성은 주장하지 않는다.
후보 실행 전에 질문·의미 계약·코드 해시를 고정했고 실행 후 기대값을 바꾸지 않았다.

첫 새 평가 시도는 10개 응답 뒤 제공자 429로 중단됐다. 쉬지 않고 자동 재시도하지 않았으며,
간격을 두고 전체 16문항을 새 배치로 한 번 실행해 통과했다. 중단된 10개는 완료 점수에서
제외했다. 진단·거절 후보를 포함한 실제 시도는 105회, 응답은 104회, 429는 1회다.
완료된 최종 후보 점수와 실패 후보·불완전 배치의 호출 수를 섞지 않는다.

## 의미 채점도 코드로 검증

`check_olist_semantics.py`는 배치와 사전 계약의 문항 집합·매니페스트 해시를 대조하고,
요약의 PASS를 그대로 신뢰하지 않고 해시가 맞는 평가 질문·기준선·실제 결과로 동작 검사를
다시 계산하며, 정확한 사유와 조사 범위를 함께 확인한다. 파일 누락·잘못된 계약·
일치하지 않는 해시는 실패한다. Olist 고정 표본에서는 분자·분모와 미관측/0건 구분도 검사한다.

```sh
uv run --locked python scripts/check_olist_semantics.py \
  --batch evidence/olist-boundary-fix-20261008/acceptance-retry \
  --contracts data/olist/personas/boundary-semantic-contracts-v1.json
```

이 명령은 저장된 증거를 검사하므로 모델 키나 DB가 필요 없다. 새로운 실추론과는 다르다.
과거 실패 배치는 같은 채점기에서 여전히 **23/24, 종료 코드 1**이다.

새 원격 평가를 하려면 먼저 Olist 원본 검증·DB 게시를 완료하고, 키를 로컬 환경 변수에
안전하게 설정한 후 아래 명령을 사용한다. 키 값을 명령줄 인자로 넣거나 Git에 저장하지 않는다.

```sh
uv run --locked python -m llm_ops_lab.olist.evaluation \
  --engine intent-v1 --provider nvidia --allow-remote \
  --remote-model nvidia/nemotron-3-super-120b-a12b \
  --dataset data/olist/investigation-boundary-acceptance-v1.json
```

생성된 배치 경로를 의미 채점기의 `--batch`에 전달한다. 구조 채점 PASS만으로 의미 합격을
판단하지 않는다. 원격 호출은 제공자의 가용량·호출 제한을 따르며 이 명령을 자동 무한 반복하지 않는다.

## 검증 범위와 남는 운영 작업

최종 자동 테스트·Ruff 결과는 [기계 판독 보고서](../evidence/olist-boundary-fix-20261008/report.json)에 기록한다.
실제 PostgreSQL 통합 검사와 프롬프트·파서·제한 시간·읽기 전용 경계를 포함한다.
검증 전후 게시 버전과 근거가 같음을 확인했다. README 변경으로 기존 문서 검토 해시가
달라진 것은 이전 검토 기록을 별도 보존하고, README를 재검토한 내역으로 기록했다. 새 체크아웃에서 성공한 uv 빌드 안내가 stderr에
기록되는 현상을 오류로 판단하던 테스트도 수정했다. 빈 stderr 조건을 제거하고 `set -eu`의
종료 코드와 실제 보고서·그래프 재개 결과 검사를 유지했으며 해당 테스트의 재검토 해시도 기록했다.

공개 파일만으로 만든 macOS 새 체크아웃에서 `.venv`의 editable `.pth`에 hidden 속성이
붙어 모듈을 찾지 못하는 기존 환경 문제가 재현됐다. 파일 속성과 실제 import 실패를 확인한 뒤,
README 시작 명령을 기존 `bootstrap.sh`로 수정했다. 실제 환경을 `work/python-env`에 두고
`.venv`를 연결한 경우 같은 `.pth`에 hidden 속성이 없고 import가 성공했다. 숨김 속성을 붙인
외부 동작의 주체까지 확인한 것은 아니며 파일 전체 속성을 일괄 변경하지 않았다.

원격 제공자의 모델 revision은 고정할 수 없다. temperature=0, seed=42도 미래의 완전한
재현성을 보장하지 않는다. Super는 원격 평가 경로이고 기본 서비스 엔진은 `action-v5`다.
HTTP 원격 백엔드 연결, 원격 장애·취소·비용 예산 검증, AWS 배포는 이번 완료 범위 밖이다.
로컬 Qwen의 이전 품질 점수를 Super 결과로 대체하지 않는다.

## 시나리오·정리

| 시나리오 | 확인 | 증거·정리 |
|---|---|---|
| 정상 질문·분모·미관측 | 동결한 회귀/새 문항 모두 통과 | 배치와 의미 계약 보존 |
| 위험 요청·지시문 주입·혼합 | 전체 보류, 사유·도구 범위 일치 | 두 반복 배치 보존 |
| 잘못된 평가 입력 | 누락·해시·ID·라벨 오류 거절 | 의미 채점기 단위 검사 |
| 과거 실패가 성공처럼 보임 | 구조 통과라도 의미 실패로 종료 | historical-failure-gate.json |
| 제공자 제한·중단 | 첫 429에서 중단, 영수증 보존 후 한 번 새 평가 | provider-recovery.json |
| 반복 변동 | 실패 후보 보존, 최종 후보 반복 검증 | 세 probe 영수증 |
| 오염·재개 상태 | 소스/질문 해시 확인, 이미 시도한 단계 자동 재실행 차단 | gate.json, runner-manifests.json |
| 기존 데이터·작업 보존 | 게시 버전·근거 불변, 원본 적재 없음 | data-preservation.json |
| 공개 경계 | 실제 키 값·키 패턴 검사, 원본과 캐시 제외 | publication-scan.json |

하네스·실패 로그는 의도적으로 증거에 보존한다. 이번 작업에서 새 서비스 프로세스나
클라우드 자원을 만들지 않았다. 실제 원격 장애를 강제로 만들거나 HTTP 복구 검사를 새로
수행한 것은 아니며, 해당 경계는 기존 자동 검사와 이전 실측 범위로 한정한다.
