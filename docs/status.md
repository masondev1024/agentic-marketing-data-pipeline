재시도·중복 이벤트·데이터 정합성과 연결해 설명해야 한다. 구현 방식은 상황에 따라 안정적 키 기반
upsert, 중복 제거, 원자적 교체 등으로 달라진다. '멱등성 = 모든 중복이 사라짐'으로 단순화하지 않는다.

## 후속 장애: editable 설치 연결 무시

2026-10-06 사용자 터미널에서 `ModuleNotFoundError: No module named 'llm_ops_lab'` 발생.
같은 환경에서 재현했으며 모듈 파일과 `.pth` 안의 소스 경로는 모두 정상 존재했다.
`.venv/lib/python3.12/site-packages/`의 `_editable_impl_llm_ops_lab.pth`와 `_virtualenv.pth`가
`st_flags=32832`였고, 이 값에 macOS `UF_HIDDEN=32768`이 포함되어 있었다.
`python -v`와 설치된 Python의 `site.py`에서 hidden `.pth`를 건너뛰는 동작을 확인했다.

첫 번째 파일에서 hidden 비트만 제거하자 모듈 import가 즉시 성공했다.
가상환경 초기화 연결 파일인 두 번째 파일에도 동일한 제한적 복구를 적용했지만,
다음 실행 전에 두 파일의 hidden 속성이 다시 붙어 import와 테스트 수집이 실패했다.

이후 가상환경을 `work/python-env/`로 옮기고 `.venv`를 상대 심볼릭 링크로 연결했다.
해당 환경 디렉터리와 두 `.pth` 파일의 hidden 비트만 제거한 뒤, 별도 프로세스에서 import와
동일 입력·생성 설정의 실제 추론을 확인했다. 실험 실행자는 assistant로 기록했다.
모델·추론 코드·잠금 의존성은 바꾸지 않았다. 숨김 속성을 설정한 프로그램은 아직 확인하지 못했다.

새 환경 구성용 `scripts/bootstrap.sh`와 프로젝트 밖 디렉터리에서 실제 설치 CLI를 실행하는
회귀 테스트를 추가했다. 기존 파일을 덮어쓰지 않으며 모델 다운로드 없이 `--help`로 설치 연결을 검증한다.

복구 후 확인: 실제 추론 성공(`runs/1f68003b-cb83-4d7a-92c2-57a3daa52798.json`),
테스트 12개 통과, lint 통과. 기존 환경에 대한 bootstrap 재실행과 별도 빈 작업 폴더에서의
새 환경 설치도 성공했고, 두 환경 모두 프로젝트 밖에서 설치 CLI를 실행할 수 있었다.
후속 프로세스에서도 `.pth` 두 파일의 hidden 비트가 해제된 상태임을 확인했다.

일반적인 문맥 제공 효과나 RAG 품질을 입증하지 않는다. 검색 단계는 아직 없다.

다음 진단 실험: 세 번째 실행의 입력 문자열과 temperature·seed를 그대로 유지하고
max_tokens만 256으로 늘린다. 출력 길이 제한과 의미/형식 오류를 분리해서 평가한다.
입력에 있던 공백까지 보존한 조건에서 prompt_tokens=132인지 확인한다.

## 학습자 출력 한도 비교 완료

증거: `runs/c891df49-f30a-4b8f-991e-d6a652975ecb.json` 및 사용자 터미널 출력.
이전 문맥 실험과 입력 문자열·실행 코드 해시가 같고, 설정은 max_tokens=128→256만 달라졌음을 확인했다.
입력 132토큰, 출력 134토큰, `max_tokens_reached=false`, 생성 약 0.82초, MLX 최고 메모리 약 0.54GB.
답변 잘림은 해소됐지만 부정확한 표현과 두 문장 지시 위반은 남았다.
단일 실행의 속도 차이를 최적화 효과로 해석하지 않는다.

다음 학습 작업은 학습자가 `src/llm_ops_lab/cli.py`의 messages에 system 역할 메시지를 추가하고,
실험 결과 JSON에도 실제 messages를 저장하는 것이다. 같은 문맥 입력과 temperature=0,
max_tokens=256, seed=42를 유지해 비교한다. system 지시는 모델 가중치를 갱신하지 않으며,
형식 준수를 강제하는 검증기와도 다르다. 후속 사용자 변경과 실행 증거는 아래에 기록한다.

## 학습자 system 메시지 구현 리뷰

사용자가 messages에 system 역할 메시지를 추가했고, 결과 JSON에 messages를 저장했다.
사용자 터미널 출력에서 기존 테스트 12개와 lint 통과를 확인했다.
실제 코드와 `runs/9373fb61-e2c2-4f3a-b7bd-2e50b656a193.json`을 읽어 다음을 검증했다.

2. 실행 JSON에 두 역할과 실제 내용이 기록된다.
3. JSON의 runner_sha256이 현재 소스와 일치한다.

입력 토큰은 132→185, 출력은 134→42, 생성 약 0.42초, 한도 도달 없음.
답변은 멱등성의 정의를 대체로 올바르게 설명했고 이전의 이상한 표현과 번호 목록은 사라졌다.
그러나 한 문장만 생성해 정확히 두 문장이라는 지시를 어겼으며,
재시도·중복 이벤트와 결과 정합성을 연결하는 필요성 설명은 부족하다.
판정: 입력 구성·기록 구현은 확인, 의미적 품질과 지시 준수는 부분 개선/미통과.
기존 단위 테스트는 새 프롬프트의 의미적 품질을 보증하지 않는다.

학습자 이해 확인 질문: system 메시지를 추가한 이번 작업이 파인튜닝이 아닌 이유는 무엇인가?
이후 단계는 참고 내용을 별도 문서 파일로 분리하고 파일 읽기·입력 검증·출처 기록을 구현하는 것이다.

## 문서 입력 기능 구현

사용자의 '바로 ㄱㄱ' 요청 범위에서 assistant가 단일 문서 파일 입력 기능을 구현했다.
학습자의 system 지시를 그대로 유지하고 build_messages 함수로 이동했으며,
문서 사용 시에만 문서 내부 지시를 참고 정보로 취급하라는 안내를 덧붙였다.
파일 읽기와 생성 엔진을 분리해 문서 계약을 GPU 없이 테스트할 수 있게 했다.

최대 16 KiB의 비어 있지 않은 UTF-8 일반 파일을 요구한다. 누락·크기 초과·인코딩 오류·빈 본문·폴더를
검사하며 읽기에도 크기 한도를 적용한다. sources에는 실제 읽은 원문 바이트의 해시와 경로를,
messages에는 실제 입력 본문을 저장한다. source_sha256에 두 소스 모듈을 기록한다.
기존 직접 입력 방식과 선택 필드가 없는 과거 실행 JSON은 유지한다.

구현 전 새 테스트의 context 모듈 import 실패를 확인한 후 구현했다.
전체 22개 테스트와 lint가 통과했다. 검증에는 파일 변경에 따른 해시 변화, 입력 바이트 경계,
잘못된 문서 거절, 문서·질문의 모델 메시지 반영, 누락 파일의 모델 import 전 실패가 포함된다.
단일 파일 입력 구현은 자동 검색이나 전체 RAG 구현 완료가 아니다.

실제 모델 검증: assistant 실행 `e4e45552-f566-44bd-9ff0-e868f4668c94`, 입력 346토큰,
출력 74토큰, 생성 약 1.13초, MLX 최고 메모리 약 0.75GB, 잘림 없음.
[보존한 실행 JSON](../evidence/day02-assistant-document-input.json)의 문서 SHA-256·바이트 수가
실제 파일과 같고, messages에 파일 본문이 포함되며, 두 소스 모듈 해시가 현재 코드와 같음을 검증했다.

답변은 재시도·중복 이벤트 자체를 막는다는 부정확한 표현을 포함했고 한 문장으로 답했다.
문서 입력과 추론 경로는 통과했지만 의미적 정확성과 두 문장 지시 준수는 통과하지 못했다.
다음 사용자 작업은 docs/day-02.md의 파일 입력 명령 실행과 문서 변경 전후 해시 비교다.

## 키워드 검색과 생성 연결 구현

사용자의 '바로 ㄱㄱ' 요청에 따라 assistant가 --corpus-dir와 --search-only를 구현했다.
기존 학습자 편집 idempotency.md는 유지하고 학습용 retry.md, backfill.md를 추가했다.
한글 조사 일부 정규화/두 글자 표현·영문 단어, 역문서빈도 가중 겹침, 첫 줄 가산으로 순위를 계산한다.
본문 겹침 0.5 미만, 매칭 표현 부족, 상위 두 후보의 점수 비율 0.95 이상은 선택을 보류한다.
이 값은 개발 기준선 휴리스틱이고 정답 확률이나 검증된 운영 임계값이 아니다.

초기 개발 예제에서 멱등성·백필 질문이 잘못 보류됐다. 질문·문서의 조사 차이로 매칭이 누락되는 것을
확인해 조사 정규화를 추가했으며, 기대값이나 임계값을 낮춰 통과시키지 않았다.
알고 있는 개발 smoke 예제 6개는 최종 6/6 통과했다. 이는 held-out 검색 정확도나 생성 품질 지표가 아니다.
전체 테스트 37개 및 lint 통과. 동점 보류, 손상 파일에서 전체 실패, 32개 한도,
파일 수정·삭제 후 변경 반영, 검색만/보류 경로의 모델 import 금지, CLI 옵션 충돌도 검증했다.

실제 CLI 증거는 [검색 검증 JSON](../evidence/day03-assistant-retrieval.json)에 보존했다.
검색만: retry.md 선택, model_executed=false.
범위 밖 날씨 질문: low_overlap으로 보류, model_executed=false.
멱등성 질문: idempotency.md 선택 후 실제 모델 생성, 기존 의미·형식 오류 지속.
재시도 질문: retry.md 선택 후 실제 모델 생성. 모델이 최대 횟수 5회를 재시도 간격 5회로 잘못 답했다.
두 생성 사례는 검색 선택 통과, 답변 품질 미통과로 구분한다.
문서 집합·선택 본문·코드 해시와 실제 모델 입력을 검증했다.

새 실행 스키마는 v2이며 generated/search_only/abstained와 model_executed로 생성 여부를 구분한다.
기존 v1 실행 파일은 보존했다. 영구 인덱스·청킹·벡터 DB·학습자 검색 실습·전체 품질평가는 아직 미완료다.
다음 사용자 작업은 docs/day-03.md의 검색만/실제 생성 비교다.

## 학습자 검색과 생성 비교

검색만 실행 `f4374eb2-6b75-41a6-910a-bdcf0138f16a`와 생성 실행
`e55c4051-e910-4c35-88c3-75aaad1630ca`를 확인했다.
질문과 문서 집합 해시가 같고 두 실행 모두 retry.md를 선택했다.
생성에 사용한 원문 해시가 실제 파일과 일치하고 messages에 본문이 포함됐음을 검증했다.
검색만 실행은 model_executed=false, 생성 실행은 true였다.

문서는 backoff/jitter로 간격을 조정하고 예시 최대 시도 횟수를 5회로 정한다.
모델은 '간격은 5회이고, 최대 시도 횟수는 5회'라고 한 문장으로 답했다.
간격에 횟수 단위를 사용한 사실/관계 오류, backoff/jitter 설명 누락,
두 문장 요구 미충족으로 판정한다. 출력 33토큰이고 잘림은 없었다.
이 사례의 관측된 실패 위치는 검색 결과 이후의 생성 단계이며,
모델 크기·프롬프트 형태 중 어느 요인이 근본 원인인지는 아직 분리 실험하지 않았다.
다음 사용자 작업은 범위 밖 질문에서 Python이 생성 전에 보류하는 경로 확인이다.

## 학습자 검색 결과 부족에 따른 보류 확인

학습자 실행 `bb88dff1-ff63-4763-86c7-5a4f6ca5b4ad`를 확인했다.
날씨 질문은 reason=low_overlap, selected_source=null, status=abstained,
model_executed=false로 기록됐다. model_id/model_revision은 null이고 messages/sources는 비어 있으며,
생성 토큰이나 모델 메모리 수치는 기록되지 않았다. 기존 테스트는 이 경로에서 모델 import 금지도 검사한다.
이번 보류는 Python 검색 규칙이 생성 전에 결정했다. 모델이 스스로 모르는 것을 알아챘다고 설명하지 않는다.
이 한 질문의 보류가 모든 범위 밖 질문이나 환각을 차단한다는 증거는 아니다.

기초 검색 실습의 세 경로(검색만, 선택 후 생성, 선택 보류)를 학습자가 실행했다.
단일 문서 변경 추적도 확인됐다. 답변의 사실/관계 오류와 형식 미준수는 계속 미해결이다.
다음 우선순위는 고정된 개발 평가 질문·정답 기준으로 검색 선택과 생성 품질을 분리해 기록하고,
동일 조건에서 프롬프트 또는 모델 변경을 비교하는 것이다. 공개 배포 준비 완료로 간주하지 않는다.

## 고정 개발 평가 실행기 — assistant 검증

자동 채점은 문서 선택/보류 및 실행 경로에 한정하며, 의미 정확성과 형식은 review.md에서 검토한다.

assistant 검색 배치 `a351b1fd-e88f-4ce0-ad7f-0e450516910f`와
생성 배치 `f6c9fa5d-2a5e-4017-91f7-66ea3cd8bbe8`를 실제 실행했다.
두 배치의 평가셋·문서·조건·소스 해시가 일치함을 확인했다. 각 배치 실행 오류는 0/20이다.
둘 다 문서 선택/보류 기대와 18/20 일치했다: 정답 문서가 있는 문항 14/15, 보류 기대 4/5.
생성 배치는 15문항에서 모델을 실행했고 5문항은 검색 단계에서 보류했다.

- retry-unknown-seconds: 관련 문서를 선택해 정확한 값이 없음을 설명해야 했으나 검색에서 보류했다.
- unknown-private-backfill: 실제 회사 기록이 없어 생성 전 보류가 목표이나 학습용 문서를 선택했다.
  모델 출력은 실제 위치와 ID가 문서에 없다고 밝혔으며 값을 날조하지는 않았다.
- retry-policy: 실제 생성에서 여전히 '간격은 5회'라는 단위/관계 오류가 발생했다.
- idempotency-recovery: 문서와 반대로 '장애 후 재시도를 금지해야 한다'고 답했다.

개발셋의 관측된 실패를 보존했으며, 통과시키려고 라벨이나 검색 임계값을 수정하지 않았다.
18/20은 답변 정확도가 아니다. 답변 의미의 전체 정답률은 아직 미산출이고 일부 사례만 assistant가
검토했다. [검증 증거](../evidence/day04-assistant-evaluation.json)에 기록과 검토자를 남겼다.

pytest 56개와 ruff가 통과했다. 데이터 계약 오류의 조기 거절, 입력 사본 고정,
독립 배치의 기존 결과 보존, 시간 초과 뒤 다음 문항 실행, 코드 해시 변경 감지,
오류의 분모 유지, 잘못된 의미의 답변을 자동 통과시키지 않는 경계를 검증했다.
시간 초과 후 다음 문항 진행 테스트는 TimeoutExpired를 주입한 테스트이며 실제 모델 hang 재현은 아니다.
학습자의 이번 평가 실행과 수동 채점은 아직 확인하지 않았다.

다음 학습자 작업은 [평가 실습](day-04.md)의 명령으로 배치를 실행한 뒤 retry-policy와
unknown-private-backfill을 직접 채점하는 것이다. 잠금 테스트셋 20문항, 프롬프트/모델 비교,
API 및 운영 검증은 아직 남아 있다.

## 검색 표현과 근거 범위 판정 구현

--retriever scoped-v2를 추가했다. baseline 기본값은 보존했다.
