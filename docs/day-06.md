# 실습 6 — 모델 선택과 비용 비교

## 결과와 결정

Qwen3-4B를 다음 개발 단계의 우선 후보로 추천한다. 기존 CLI 기본값은 재현성을 위해
0.6B로 보존했으며, 4B는 --model qwen3-4b로 선택한다. 서비스 배포 준비가 끝났다는 뜻은 아니다.

| 측정 | Qwen3-0.6B | Qwen3-4B |
|---|---:|---:|
| 필수 내용 + 근거 충실성 통과 | 4/15 | 10/15 |
| 생성한 범위 내 답변의 두 문장 형식 | 0/14 | 9/14 |
| 검색 선택/보류 일치 | 18/20 | 18/20 |
| 범위 밖 질문 생성 전 보류 | 4/5 | 4/5 |
| 생성 시간 중앙값 | 0.50초 | 4.16초 |
| 출력 토큰 중앙값 | 36.5 | 62.0 |
| 모델 로딩 시간 중앙값 | 0.59초 | 1.53초 |
| MLX 최대 메모리 | 0.86GB | 2.98GB |
| 출력 토큰 한도 도달 / 실제 생성 | 0/15 | 0/15 |
| 실행 오류 | 0/20 | 0/20 |

내용과 형식은 assistant 수동 판정이다. 내용 평가는 정답 문서가 있는 15문항이며
검색 누락 1건도 분모에 유지했다. 형식 평가는 실제 생성한 범위 내 14문항이다.
성능 시간 집계는 모델별 첫 생성 문항을 제외한 동일한 14개 생성 질문에 대해 계산했다.
첫 생성은 시작 비용과 초기 기준선의 로컬 가중치 해시 확인 작업 영향을 제외하기 위해 빼고,
품질과 최대 메모리 집계에는 그대로 포함했다. 다운로드와 겹친 사전 배치는 시간 비교에서 제외했다.
출력 길이도 달라졌고 호스트의 다른 작업 부하는 통제하지 않았으므로 고립된 속도 벤치마크가 아니다.

두 모델의 질문/문서/루브릭/코드/생성 설정/프롬프트가 동일함을 확인했다.
실제로 전달한 메시지와 입력 토큰 ID 해시도 모든 문항에서 일치했다.
새 코드에서 0.6B의 전체 답변은 이전 기준선과 동일했다.

기존 내용+근거 통과 문항의 퇴행은 없었고 6개 문항이 추가 통과했다.
retry-policy와 idempotency-recovery가 모두 내용/근거 기준을 통과했고,
오류 0건·MLX peak 4GB 이하를 충족해 실험 전 세운 다음 단계 후보 기준을 만족했다.
이 결정은 단일 seed의 개발셋 결과에 한정한다.

## 주요 답변 변화와 남은 문제

- retry-policy: '간격은 5회'에서 '간격은 backoff/jitter, 최대 횟수는 5회'로 개선했다.
- idempotency-recovery: 재시도 금지라는 반대 주장을 고쳤지만 세 문장을 출력해 형식은 실패했다.
- idempotency-sales: 이벤트 ID와 매출/이력의 단일 트랜잭션을 모두 설명하게 됐다.
- retry-jitter: 여전히 backoff/jitter가 요청 중복을 방지한다고 잘못 설명했다.
- retry-timeout: 중복 반영 방지는 설명했지만 타임아웃이 서버 미처리의 증거가 아니라는 사실을 누락했다.
- backfill-prepare: 날짜 구간과 입력/코드 버전은 맞았으나 고정 루브릭의 출력 위치를 누락했다.
- backfill-concurrency: 중첩 확인 대상을 부정확하게 설명했고 저장소 트랜잭션/스냅샷 조건을 누락했다.
- unknown-private-backfill: 답변에서 실제 정보가 없다고 명확히 밝혔지만, 목표인 생성 전 보류에는 실패했다.

idempotency-why의 첫 문장은 어색하다. 전체 답변이 반복 처리의 중복 위험과 일관성 보장을
연결하는 의미를 전달한다고 보아 통과로 판정했으며, 특정 단어의 존재 여부로 채점하지 않았다.
표현의 명료성과 판정자 간 일치는 추가 검토 대상이다.
또한 일부 질문은 루브릭보다 좁게 읽힐 수 있다. 예를 들어 버전 정보를 묻는 질문의 기준은
출력 위치까지 요구한다. 이번 실험 중 기준을 바꾸지는 않았으며, 향후 평가셋 v2를 만들 때
질문과 요구 항목의 정합성을 검토하고 모든 비교 모델을 다시 평가해야 한다.

## 검증 기록

pytest 62개, Ruff 통과. 모델 선택과 revision 고정, 검색 전 보류에서 모델 미실행 기록,
잘못된 실제 모델 정보 감지를 검사했고, 실제 두 모델의 20문항씩을 추가 실행했다.
모델 파일은 약 278초에 다운로드됐고 파일 크기와 가중치 SHA-256을 기록했다.

- 최종 0.6B 배치: 14bb628b-4207-4eef-8602-3f3e8e389f3b
- 최종 4B 배치: 8ad2d99c-87d9-418b-861c-d4e56eed3888
- 사전 0.6B 확인 배치: 0334bb33-f0ad-44d3-bbca-d93ebda23c48 (다운로드와 겹쳐 시간 비교 제외)

각 최종 배치의 review.md와 manual-review.json에 20문항의 판정 근거를 작성했다.
학습자의 새로운 실행이나 판단으로 기록하지 않았다.

## 실험 질문

프롬프트 강화 실험에서 내용·근거 동시 통과가 개선되지 않았다.
이번에는 프롬프트, 평가셋, 문서, 검색기를 그대로 두고 모델 체크포인트를 바꾼다.
이는 추론에 사용하는 모델을 교체하는 실험이며 파인튜닝이 아니다.

기준선은 mlx-community/Qwen3-0.6B-4bit,
후보는 mlx-community/Qwen3-4B-4bit다. 둘 다 같은 Qwen3 계열의 4bit MLX 모델이다.
서로 다른 크기로 훈련된 모델을 비교하므로 개선 원인을 매개변수 수 하나로만 단정하지 않는다.

- [MLX 변환 모델 카드](https://huggingface.co/mlx-community/Qwen3-4B-4bit)

원격 Python 코드를 허용하지 않는다. 모델 파일은 Git에서 제외한다.
최초 다운로드 후 평가 자체는 --offline으로 진행한다.

## 고정 조건과 채택 기준

baseline 시스템 프롬프트, temperature=0, max_tokens=256, seed=42,
enable_thinking=false를 두 모델에 동일하게 적용한다. 같은 평가 실행 코드에서 각각 실행하고,
평가셋·문서·실제 메시지와 입력 토큰 ID 해시를 대조한다.

검토자는 assistant이며 개발용 20문항의 기존 루브릭으로 문항마다 판정한다.
주지표는 문서가 있는 15문항의 필수 내용+근거 충실성 동시 통과다.
검색 실패도 분모에서 제외하지 않는다. 생성한 범위 내 14문항의 두 문장 형식,
범위 밖 5문항의 생성 전 보류는 별도 집계한다.

후보를 다음 개발 단계에 추천할 기준: 주지표 증가, 기존 통과 문항 퇴행 없음,
retry-policy와 idempotency-recovery 내용/근거 통과, 실행 오류 없음,
관측한 MLX 최대 메모리 4GB 이하. 배포 승인이나 서비스 품질 보증 기준이 아니다.
기존 CLI 기본 모델은 재현성을 위해 0.6B를 유지하고 후보는 명시적 옵션으로 선택한다.

## 실행 방법

아래 오프라인 명령은 해당 모델이 이미 캐시되어 있을 때 사용한다.
현재 실습에서 assistant가 후보 다운로드 및 검증을 수행한다.

```sh
uv run --locked python -m llm_ops_lab.evaluation --offline \
  --model qwen3-0.6b --prompt-variant baseline \
  --temperature 0 --max-tokens 256 --seed 42

uv run --locked python -m llm_ops_lab.evaluation --offline \
  --model qwen3-4b --prompt-variant baseline \
  --temperature 0 --max-tokens 256 --seed 42
```

단일 질문에도 llm-lab --model qwen3-4b를 사용할 수 있다.
지원 모델만 허용하고 각각 revision을 고정한다. model_profile은 선택한 설정이며,
실제 사용한 model_id/model_revision은 생성한 경우에만 추론 기록에 들어간다.
검색에서 보류한 경우 후보 설정이 있어도 model_executed=false다.

## 운영 관점의 피드백

- 테스트 통과와 모델 정답률은 다르다. Python 테스트는 모델 선택 전달과 기록의 일관성을
  검증하고, 실제 답변은 모델을 실행한 뒤 같은 루브릭으로 별도 검토한다.
- 검색 실패를 큰 모델로 해결했다고 주장하면 안 된다. 모델 호출 이전에 근거를 놓쳤다면
  모델 크기를 바꿔도 해당 경로는 그대로다.
- 출력이 길어지면 답변에 필요한 항목을 더 포함할 수도 있지만 생성 시간도 늘어난다.
  생성 시간과 함께 출력 토큰 수를 읽어야 한다.
- MLX peak는 MLX가 추적한 최대 메모리이며 프로세스 RSS나 전체 Mac 메모리가 아니다.
  문항마다 새 프로세스이므로 로딩 비용도 있고, 결과를 상시 로딩 서버의 처리량으로 해석할 수 없다.
- 단일 seed의 15개 실제 생성으로 p95나 서비스 SLO를 확정하지 않는다.
  이 단계는 모델 후보 선별이며 잠금 테스트셋·반복 측정·API 동시성 검증은 남아 있다.
