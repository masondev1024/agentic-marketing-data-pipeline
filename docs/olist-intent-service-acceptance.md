# Olist 요청 분류·근거 실행 서비스 검증 — 2026-10-08

판정: **운영 제어는 통과, 자연어 품질 승격은 보류**. 개발 평가 18/18과 별도 최초 평가
21/24는 서로 다른 의미다. 혼합 요청을 누락한 사례가 있으므로 87.5%를 합격으로 바꾸지 않는다.
기본 HTTP/CLI 엔진은 기존 `action-v5`를 유지한다. 새 `intent-v1`은 명시적으로 선택하는
평가 후보이며, 기존 엔진도 운영 서비스 수준의 의미 판별 품질을 보장하지 않는다.

## 구조를 바꾼 이유

모델이 SQL 도구와 최종 진단을 자유롭게 선택하면, 올바른 답 옆에 요청하지 않은 진단을
추가하거나 요청 일부만 처리하고 완료라고 표시할 수 있었다. 새 경로에서는 모델의 역할을
요청 분류로 제한했다.

`질문 → 타입 검사된 요청 목록 → 호스트의 거절 우선 판정 → 고정 읽기 도구 → 근거 기반 결과`

- 지원 범위: origin 누락·분모, 계약의 판매자 표본 연결, 최근 실행 이력, 게시 품질 검사.
- 모델은 등록된 라벨만 출력한다. 호스트가 도구와 진단 코드를 정한다. 임의 SQL/쓰기 없음.
- 지원 불가 부분이 하나라도 분류되면 전체 요청을 보류한다. 위험·원인 확정·범위 밖 요청은
  DB 세션을 열기 전에 보류한다. 금액·귀속 지표는 버전별 definitions 근거 조회 후 거절하므로
  이 경로는 DB 가용성에 의존한다.
- 모델 형식 수정은 한 번만 허용한다. 세션은 읽기 전용 동일 스냅샷, 모델·조회는 같은 마감 시각을
  공유한다. 출력·입력 토큰과 응답 크기에도 상한이 있다.
- 확인된 0건, 빈 관측, 누락된 필드를 구분한다. 0건이 전체 원천의 완전성이나 미래 무장애를
  의미하지 않는다. 분자·분모는 같은 게시 채널 집계에서 산출한다.
- 타임아웃 등으로 모델이 응답을 반환하지 못하면 `model_execution_status=attempted_unknown`을
  기록한다. `model_executed`는 응답을 받은 실행만 뜻한다.

분류 모델이 지원 불가 요구 자체를 놓치면 호스트의 거절 규칙도 발동하지 않는다. 이것이
현재 남은 핵심 한계다. 스키마 검증과 읽기 전용 권한은 의미 판별의 정확성을 대신하지 않는다.

## 평가 결과와 한계

| 평가 | 결과 | 해석 |
|---|---:|---|
| 개발용 기존 질문 | 6/6 | 프롬프트 개발에 사용된 회귀 사례 |
| 개발용 역할 변형 질문 | 12/12 | 독립 평가가 아님 |
| NVIDIA 페르소나 기반 최초 평가 | 21/24 | 프롬프트/후보 고정 뒤 처음 실행 |
| 실제 모델 HTTP 운영 검사 | 16/16 | 생성·큐·복구·로그 검증; 답변 의미 합격과 구분 |
| NVIDIA 어댑터 모의 HTTP 검사 | 37/37 | 실제 NVIDIA 모델 호출/품질 증거가 아님 |

최종 전체 테스트 **650개 통과, 건너뜀 0개**, Ruff 통과다. 재검증 경로는 [기계 판독 보고서](../evidence/olist-intent-acceptance-20261008/release-review.json)에 기록한다.

실패는 다음 세 가지다.

1. `finance_30day_sales`: 안전하게 보류했지만 금융 정책 사유와 definitions 근거를 빠뜨렸다.
2. `finance_mixed_origin_roas`: origin만 처리하고 ROAS 계산 요구를 놓쳐 부분 결과를 완료로 표시했다.
3. `rootcause_mixed_status`: 실행 이력만 조회하고 원인 확정 요구를 놓쳤다. 전체 보류 및 0회 조회 계약 위반이다.

최초 24사례에 대한 독립 검토도 이 실패를 확인했다. 최초 출력에는 분모 숫자가 요약에서
빠진 완전성 문제가 추가로 있었다. 그 후 호스트 렌더러에 `observed_counts`와 분모 표시를
추가했다. 분류 프롬프트는 바꾸지 않았다. 이후 같은 24문항 실행은 **회귀 검사**로만 기록한다.
깨끗한 관측 코드 등록·원격 평가 옵션은 최초 평가 뒤의 계약 보강이다. 최초 후보 해시와 최종
소스 해시를 별도로 보존한다.

최초 합격 기준은 개발 18/18, 별도 평가 24/24, 주요 거절 반복 3회와 운영 검증 통과였다.
최초 평가부터 실패했으므로 거절 반복을 합격 증거로 쌓는 단계와 기본 엔진 승격은 진행하지
않았다. 5회 프롬프트 실험 후 멈췄고, 실패 질문에 맞춘 추가 프롬프트 조정은 하지 않는다.

## NVIDIA 페르소나 사용 범위

[NVIDIA Nemotron-Personas-Korea](https://huggingface.co/datasets/nvidia/Nemotron-Personas-Korea)의
공개 합성 페르소나 12개를 수집했다. 전체 다운로드는 약 103KB이며 큰 데이터셋 전체를 받지
않았다. 페르소나는 실제 고객 개인정보가 아니다. 실제 거래·리드 데이터는 별도의 Olist 표본이다.

다른 작성 에이전트가 역할/업무 맥락을 사용해 24문항과 기대 계약을 작성하고 해시를 고정했다.
NVIDIA 모델이 질문을 생성하거나 정답을 자동 판정했다고 주장하지 않는다. 표본 출처·변형
매핑·CC-BY-4.0 attribution은 `data/olist/personas/acceptance-provenance-v1.json`에 있다.
저장한 응답 바이트를 SHA-256으로 고정했지만 datasets-server가 특정 저장소 revision에
연결됐다는 보증은 없으므로, 관측한 HF revision을 샘플의 고정 revision으로 주장하지 않는다.

## 운영 검증

실제 Qwen3-4B를 하나의 워커에서 사용했다. 동시에 보낸 6요청 중 3개는 수락하고 3개는
429로 거절했다. 워커 정지를 주입한 요청은 504로 끝났고, 이전 워커 회수 후 교체 워커가
실제 모델 응답을 다시 생성했다. 이 검사는 자연 발생 장애가 아니라 의도적 fault injection이다.
요청 ID·접근 로그·실행 파일의 연결, 소유 프로세스와 포트 정리도 검증했다.

초기 전체 테스트를 모델 평가와 동시에 실행해 공용 모델 잠금 테스트 1개가 실패한 기록이
있다. 잠금을 약화하지 않고 최종 테스트를 순차 실행했다. 중간 실패 로그도 보존한다.
PostgreSQL 통합 검사는 별도 임시 DB에서 수행하며 기존 게시 버전과 조사 근거는 보존했다.
AWS 배포, 외부 트래픽, 장기 SLA, 실시간 소스의 운영 안정성은 이번 검증 범위가 아니다.

## 다음 모델 비교 준비

`NvidiaPlanner`는 평가 전용 선택 사항이다. HTTP 서비스의 자동 폴백으로 연결하지 않았다.
고정 NVIDIA HTTPS 주소, 리디렉션 금지, 환경 프록시 비활성화, 전체 요청 타임아웃,
응답 크기·토큰·호출 수 제한, 비밀을 포함하지 않는 오류 코드가 적용됐다.

일반 DB 결과를 모델에 보내지 않는다. 분류용 시스템 지침과 평가 질문만 전송한다. 단,
`--dataset`을 바꾸면 그 파일의 질문이 전송되므로 비공개 자료를 넣은 평가셋을 사용하지 않는다.
호스팅 모델은 가중치 revision을 고정할 수 없으므로 로컬 모델과 동일한 재현성을 주장하지 않는다.

공개 페르소나 다운로드에는 키가 필요 없었다. 실제 NVIDIA 모델 비교에는 사용 가능한 모델
ID와 계정 권한·크레딧 확인이 필요하다. 특정 무료 모델이 계속 제공된다고 가정하지 않는다.
[NVIDIA 모델 카탈로그](https://build.nvidia.com/)와
[공식 API 문서](https://docs.api.nvidia.com/nim/reference/llm-apis)를 기준으로 확인한다.

키는 채팅에 붙이지 않고 로컬 `work/olist/secrets/nvidia-api-key.txt`에 저장한다. 이 파일은
Git에서 제외되고 소유자만 읽고 쓸 수 있다. 파일이 비어 있으면 외부 호출 전에 중단한다.

```bash
# 계정에서 이용 가능한 정확한 MODEL_ID와 체험 한도를 확인한 뒤 실행
uv run --locked python work/olist-intent-quality/run_nvidia_pilot.py MODEL_ID
```

준비된 파일럿은 노출된 회귀 질문 6개, 질문당 최대 2회로 총 12회 호출 상한이다. API/형식
검증이 실패하면 안전하게 보류하며 자동 재시도·무료 모델 탐색 호출·클라우드 생성은 없다.
파일럿 성적을 새 독립 평가로 주장하지 않는다. 더 강한 모델이라고 자동 합격하지 않으며,
후보가 결정되면 새로운 별도 평가와 거절 반복 검증이 필요하다.
