## 사용자 목표

챗봇 개발·모델 구축·개선 경험이 없는 상태에서, 이번 주에 LLM 서비스의 수직 단면을
직접 구현·측정·설명한다. 취업 자료에는 검증된 결과와 본인 작업만 기록한다.
아래 날짜는 목표이며 학습 진척과 실제 평가 결과에 따라 범위를 조정한다.

## 제품

데이터 파이프라인 운영 문서를 근거로 장애 원인 후보와 확인 절차를 설명하는 읽기 전용 서비스.
처음에는 직접 작성한 소규모 가상 운영 문서만 사용한다. 잘못된 명령 실행은 제품 범위 밖이다.
질문에 충분한 근거가 없으면 답변을 보류하고 필요한 정보를 요청한다.

## 아키텍처 초안

오프라인: Markdown 원문 → 계약 검증 → 정규화·청킹 → 검색 인덱스 버전.
온라인: 질문 → 입력 제한 → 검색 → 근거 포함 프롬프트 → 로컬 MLX → 출처 검증 → 답변/보류.
별도: 고정 평가셋 → 실행 결과 → 오류 분류·품질·지연·비용 보고서.

문서 계약은 `document_id`, `version`, `source`, `updated_at`, `content_hash`를 포함한다.
원문과 파생 인덱스를 구분하고, 소스가 바뀌면 해당 문서 청크를 교체하는 멱등 갱신을 설계한다.
인덱스 구축 실패 시 기존 버전을 유지하고 완료된 새 인덱스로만 전환한다.
데이터 규모에 맞는 단일 프로세스·로컬 저장부터 시작한다. Spark/Kafka/Kubernetes는
이 범위에서 증명할 요구가 없어 초기 의존성으로 넣지 않는다.

## 검증 기준과 해석

- 품질 평가: 개발 20문항과 잠금 테스트 20문항, 질문뿐 아니라 문서/시나리오 단위 중복도 검사.
- 검색 평가: 정답 근거 문서가 top-k 안에 들어오는 비율과 실패 사례를 별도로 기록.
- 생성 평가: 사실·근거·출처·보류 기준을 사람이 검토. 모델 자기평가만으로 통과시키지 않음.
- 잠금 테스트 합격 목표는 근거가 충분한 질문의 정답+출처 적합률 80% 이상,
  근거 부족 질문의 적절한 보류율 90% 이상. 각 분모와 실제 개수를 함께 공개.
  작은 평가셋이므로 광범위한 품질 보증이 아니며 목표 미달은 그대로 보고.
- 동일 문서 재처리, 문서 수정·삭제, 인덱스 빌드 실패 후 이전 버전 사용을 검증.
- 프롬프트/모델/문서/인덱스 버전과 요청 ID로 답변 재현 경로를 남김.
- 지연은 장비·입출력 길이·요청 수를 고정한 반복 실험으로 측정.
  p95는 최소 100요청에서 표본 수와 함께 기록하고, 초기 측정 후 서비스 목표를 정함.
- 동시성은 제한하고 용량 초과는 명시적으로 거절. 무한 재시도나 무제한 대기열 금지.
- 외부 배포 전 인증·요청 제한·비용 한도·민감정보 로그 정책을 검토.
- 외부 배포를 승인받지 못하면 결과는 로컬 서비스 검증으로 명시하며 외부 운영 완료로 처리하지 않음.

## 학습 확인

각 단계마다 본인이 입력 또는 코드를 바꾸고 결과를 설명한다. assistant의 실행은 환경 검증이며
학습자의 경험으로 간주하지 않는다. 질문 예: 대화 전달과 학습의 차이, 검색 오류와 생성 오류의 차이,
긴 입력의 메모리·지연 영향, 재시도 시 중복 방지, 답변 보류를 평가하는 방법.

## 선택 확장과 중단 기준

LoRA는 기본 서비스 평가가 완료되고 개선할 오류 유형이 명확할 때만 별도 실험한다.
Transformer 직접 구현은 이번 주 필수 범위에서 제외하고 이후 원리 심화 트랙으로 분리한다.
모델 품질이 부족하면 평가를 보고 모델 크기 또는 과업 범위를 조정한다.
예산 승인 없이 GPU 임대·유료 API·공개 배포는 하지 않는다.

## 고정 경계

첫 실습 환경: Apple M1 Pro / RAM 16GB / Python 3.12 / MLX.
모델은 safetensors와 알려진 로컬 구현으로 로드; 임의 원격 Python 코드를 신뢰하지 않음.
사용자 승인이 필요한 게시 작업: commit, push, PR, 외부 배포. 로컬 구현·검증은 진행 가능.
이 문서는 확정 성과가 아닌 실행 계획이다.
