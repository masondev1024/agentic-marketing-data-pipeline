# 검색 표현 정규화와 문서별 단어 근거 확인

`--retriever scoped-v3`를 실험 후보로 추가했다. 기존 기본값 `baseline`과 `scoped-v2`는 유지한다.
이번 단계는 assistant가 구현·실행·채점했다. 학습자의 직접 실행이나 이해 확인을 대신하지 않는다.

## 문제와 설계

이전 검색 누락 5건은 모두 정답 문서가 1위였으나 단어 일치 비율이 0.5에 못 미쳐 보류됐다.
질문 표현과 조사·어미 조각까지 분모에 들어가면서 의미가 같은 긴 질문에 불리했다.
임계값을 낮추면 관련 단어에 섞인 무관한 요구까지 통과하므로 0.5를 유지했다.

새 처리 순서는 다음과 같다.

1. 원문 문서와 `scope.json`의 내용 해시 계약을 검증한다.
2. 기존 scope 정책으로 실제 회사·실행 기록이 필요한 질문을 보류한다.
3. 검색용으로만 제한된 조사·어미와 질문 표현을 정규화한다.
4. 정규화한 문서 본문과 제목으로 순위를 계산하고 기존 점수·동점 판정을 적용한다.
5. 1위 문서에 없는 핵심 단어가 남으면 `unsupported_query_terms`로 보류한다.
6. 선택한 원문 문서와 **사용자가 입력한 원래 질문**을 모델에 전달한다.

지원하지 않는 문자·문자열이 토큰화 중 사라지지 않도록 원래 질문도 검사한다.
한글 음절과 ASCII 중심 처리 범위를 벗어나는 문자·기호·제어문자가 있으면
`unsupported_query_characters`로 보류한다. 여러 언어를 지원하는 검색기를 구현한 것은 아니다.

예를 들어 `재시도 간격 최대 시도 횟수 API 요청 오류와 환율은?`은 일치 비율이 0.5 이상이어도
`환율`의 근거가 없어 보류한다. 다른 문서에만 환율이 있어도 1위 문서의 근거로 인정하지 않는다.
환율이라는 단어를 금지한 것은 아니다. 선택 문서 자체에 해당 내용이 생기고 계약도 갱신하면
단어 근거 검사를 통과할 수 있다. 단어가 있다는 사실은 질문의 관계나 전제가 참이라는 뜻은 아니다.

## 검색 결과

같은 코드·문서·평가셋에서 검색기 옵션만 바꾼 검색 전용 배치를 실행했다.

| 평가셋 | scoped-v2 | scoped-v3 | v3 문서 선택 대상 | v3 보류 대상 |
|---|---:|---:|---:|---:|
| 기존 개발 20문항 | 20/20 | 20/20 | 15/15 | 5/5 |
| 추가 검증 20문항 | 15/20 | 20/20 | 10/10 | 10/10 |
| 관련 질문·혼합 질문 대조 24문항 | 19/24 | 24/24 | 12/12 | 12/12 |

각 수치는 예상 문서 선택 또는 보류와 일치한 개수다. 실행 오류는 여섯 배치 모두 0건이다.
문서 선택 대상에는 “문서에 정확한 초 값이 있는가”처럼 문서를 읽고 정보 부재를 답해야 하는 질문도
포함된다. 검색 통과를 답변 정답이나 질문의 전제가 참이라는 판정으로 해석하면 안 된다.

세 평가셋 모두 개발에 사용됐다. 새 24문항도 기존 사례를 확장한 대조 질문이며 독립 테스트가 아니다.
라벨을 바꾸지 않고 실패 원인을 분석해 코드를 수정했지만, **64/64가 일반 질문 정확도 100%를 뜻하지 않는다.**
기존 v2의 40문항은 이전 저장 결과와 판정·순위·점수가 같은지도 확인했다.

## 실제 모델 답변

복구된 5문항만 Qwen3-4B 4bit, baseline 프롬프트, temperature 0, max-tokens 256, seed 42로
오프라인 실행했다. 신규 다운로드는 하지 않았다. 최종 배치는
`abc03dd6-9f80-4d3b-8f50-59a1a5ed30ca`이며, 원래 자동 채점표와 요약은 그대로 보존했다.
별도 `review.assistant.json`과 공개 증거 파일에 수동 판정을 남겼다.

| 질문 | 필수 내용·근거 | 관측 |
|---|---|---|
| 정확한 재시도 간격은 몇 초인가 | 통과 | 문서에 구체적 값이 없다고 답함 |
| 재시도는 몇 번까지 시도하는가 | 통과 | 최대 5회를 답함. 예시 정책임을 다시 명시하면 더 명확함 |
| 우리 팀에서 재시도 횟수를 제한하는 이유 | 실패 | 오류의 반복 발생을 막는다고 주장하고 전체 시간 예산을 누락함 |
| 멱등성과 반복 횟수의 관계 | 통과 | 반복해도 한 번 수행한 효과와 같다고 답함 |
| 고정된 간격은 몇 분인가 | 통과 | 문서에 구체적 값이 없다고 답함 |

필수 내용·근거 동시 충족은 **4/5**, 두 문장 형식은 **5/5**였다.
assistant가 작성한 기준을 assistant가 검토한 결과이며 독립적인 사람의 평가가 아니다.
전체 평가셋의 생성 품질을 재측정한 것도 아니다.

횟수 제한은 재시도를 멈출 조건을 정한다. 오류 자체의 발생을 막지 않는다.
따라서 위 실패는 검색에 성공한 이후의 생성 오류다. 이 문제를 고치려고 검색 임계값을 바꾸면
원인과 관계없는 단계가 바뀌어 회귀 위험만 늘어난다.

## 실패 기록과 리뷰

첫 구현은 단어 형태를 너무 엄격하게 비교해 기존 개발셋이 10/20으로 퇴행했다.
어미·조사 처리를 보완하고, 임의 접두어 일치도 제거했다. 예를 들어 `재시도보험료`가
`재시도`로 시작한다는 이유만으로 지원된다고 판단하면 안 된다.
탐색 중 실패 결과는 증거 JSON에 별도로 남겼다. 탐색 단계에는 코드 사본이 없어 해당 결과의
완전한 재현을 주장하지 않는다. 최종 배치에는 전체 소스·문서·질문·의존성 잠금 해시가 있다.

OMC 독립 코드 리뷰와 아키텍처 리뷰를 진행했다. 아키텍처 리뷰가 발견한
`재시도 간격과 東京気温은?`의 미지원 문자 소실을 수정하고, 한자·키릴·악센트·이모지·제어문자
사례에서 모델을 import하지 않고 보류하는 테스트를 추가했다.
회사·정책·기준을 무조건 제거하던 표현 처리도 좁혔다. 최종 코드 리뷰는 APPROVE,
아키텍처는 WATCH이며 남은 언어 규칙·과적합 한계를 유지한다. 공개 배포나 운영 준비 승인은 아니다.

최종 검증은 **pytest 162개 통과, Ruff 통과**다. 새 정규화 모듈의 해시 변조도 평가 오류로 탐지한다.

## 운영 관점의 한계와 복구

- 정규화는 한국어 형태소 분석이나 의미 추론이 아니다. `정확한`, `고정`, `관계` 같은 표현 제거에도
  가정이 있다. 단어별 일치는 사실 관계·부정·수치·권한을 증명하지 않는다.
- **`재시도 횟수 상한을 알려줘.`는 아직 보류한다.** 문서의 `최대`와 `상한`을 동의어로 이해하지 못한다.
  이번 단계에서는 이 사례를 다시 맞추도록 규칙을 추가하지 않고, 새 실패 유형으로 남겼다.
- 단일 문서만 전달하므로 여러 문서가 필요한 정상 질문도 보류할 수 있다.
- 32개 문서·문서당 16KiB 제한 안에서 매번 정규화한다. 대규모 코퍼스 인덱스나 동시 요청 성능은
  검증하지 않았다. 모델 호출 전 보류 경로는 모델 추론 비용을 쓰지 않는다.
- 잘못된 계약은 입력 오류로 종료한다. 결정적인 입력 오류를 재시도하지 않는다.
  문서 변경 시 검토한 새 계약을 함께 갱신하고, 문제 발생 시 `--retriever scoped-v2`로 비교·복귀한다.
- 기록에는 정규화 전후 질문 정보, 정책 버전, 미지원 단어·문자, 원문과 코드 해시가 남는다.
  같은 설정과 문서에서 어느 단계가 판정을 바꿨는지 추적하기 위한 장치다.

## 직접 실행

프로젝트 루트에서 검색 결과부터 비교한다.

```sh
uv run --locked llm-lab --offline --search-only \
  --corpus-dir data/runbooks --retriever scoped-v3 \
  --prompt '재시도를 몇 번까지 시도하는 정책인가요?'

uv run --locked llm-lab --offline --search-only \
  --corpus-dir data/runbooks --retriever scoped-v3 \
  --prompt '재시도 간격 최대 시도 횟수 API 요청 오류와 환율은?'

uv run --locked python -m llm_ops_lab.evaluation --offline --search-only \
  --model qwen3-4b --retriever scoped-v3 \
  --dataset data/eval/retrieval-support-v1.jsonl
```

첫 질문은 retry.md 선택, 두 번째는 `unsupported_query_terms` 보류가 예상된다.
같은 명령에서 `scoped-v2`로 바꾸면 이전 결과와 비교할 수 있다.
개발셋과 추가 검증셋도 `--dataset`을 각각 `data/eval/development-v1.jsonl`,
`data/eval/retrieval-challenge-v1.jsonl`로 바꾸어 재현한다.

생성 단계의 남은 오류는 다음 명령으로 직접 확인한다.

```sh
uv run --locked llm-lab --offline --model qwen3-4b \
  --corpus-dir data/runbooks --retriever scoped-v3 --prompt-variant baseline \
  --temperature 0 --max-tokens 256 --seed 42 \
  --prompt '우리 팀에서 재시도 횟수를 제한해야 하는 이유는?'
```

학습 포인트: “올바른 문서를 찾았지만 틀리게 답했다”와 “올바른 문서를 보류했다”를
각각 어느 로그와 평가 기준으로 구분할지 설명해 본다.
