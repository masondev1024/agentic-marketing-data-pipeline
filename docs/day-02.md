# 문서 파일을 모델 입력에 연결하기

## 이번 단계의 흐름

문서 파일 → 바이트/UTF-8/비어 있음 검증 → 본문과 SHA-256 → system/user 메시지 → 토큰화 → 생성 → 기록.
모델은 파일 경로를 전달받아 직접 디스크를 읽지 않는다. Python이 읽은 본문을 입력에 넣는다.

```sh
uv run --locked llm-lab --offline \
  --context-file data/runbooks/idempotency.md \
  --prompt '데이터 파이프라인에서 멱등성이 필요한 이유를 두 문장으로 설명해 줘.' \
  --temperature 0 --max-tokens 256 --seed 42
```

## 확인할 계약

일반 파일, 최대 16 KiB, 올바른 UTF-8, 공백뿐이지 않은 본문을 요구한다.
없는 파일·폴더·한도 초과·인코딩 오류는 모델 로딩 전에 실패하고 성공 실행 JSON을 만들지 않는다.
실패를 빈 문서나 잘린 문서로 조용히 바꾸지 않는다. 원인을 고친 다음 재실행한다.
원문은 변경하지 않으며 실행 결과는 새 UUID로 저장한다.
문서 바이트 제한과 전체 입력 2,048토큰 제한은 다르다. 토큰 제한은 템플릿 적용 후 검사한다.
현재는 토큰 검사 전에 모델과 토크나이저를 로드하므로, 토큰 초과는 GPU 할당 전 차단이라고 주장하지 않는다.

## 기록을 읽는 방법

- `input`: 사용자가 입력한 질문. 파일 본문을 합친 문자열로 덮어쓰지 않는다.
- `messages`: 모델에 실제 전달한 system/user 메시지. 문서 본문을 포함한다.
- `sources`: 문서 경로, 파일 원본 바이트의 SHA-256, 바이트 수, 인코딩.
- `source_sha256`: 추론 코드와 문서 처리 코드의 해시.
- `prompt_template_version`: 문서 사용은 document.v1, 직접 입력은 manual.v1.

같은 파일 이름이라도 내용이 바뀌면 SHA-256이 바뀐다. 따라서 경로만 남기는 것보다
답변이 어떤 문서 내용으로 만들어졌는지 추적하기 쉽다. 해시 자체는 내용을 복구하지 못하므로
실제 사용 본문은 messages에도 남긴다. 공개·합성 문서만 사용한다.
기존 inference-experiment.v1 기록에는 새 필드가 없을 수 있으므로 읽는 쪽은 선택 필드로 처리한다.

## 코드 읽는 순서와 직접 할 과제

1. `src/llm_ops_lab/context.py`의 load_document: 파일 계약을 검사하고 한 번 읽은 바이트를 해싱한다.
2. 같은 파일의 build_messages: 읽은 문서와 질문을 모델 입력으로 구성한다.
3. `src/llm_ops_lab/cli.py`의 run_experiment: 문서 검증을 모델 초기화 앞에서 실행한다.

첫 실행 결과를 본 뒤, 문서 마지막에 본인이 이해한 구체적인 중복 처리 사례를 한 문단 추가한다.
모델·질문·생성 설정을 유지한 채 다시 실행하고 sources의 경로는 같지만 sha256은 달라지는지 확인한다.
답변이 달라졌는지는 별도로 평가하며, 본문을 바꿨다고 품질 개선을 가정하지 않는다.

## 검증 범위

이 실습의 --context-file은 지정한 문서 한 개를 읽는 기능이다. 자동 검색은 후속 --corpus-dir 모드에
추가했으며 [검색 실습](day-03.md)에 설명한다. 청킹·벡터 DB는 아직 없고 품질 검증 완료로 부르지 않는다.
문서 내 지시를 따르지 말라는 프롬프트는 보안 격리를 보장하지 않는다. 이 단계는 신뢰하는 로컬
공개·합성 문서를 대상으로 하며, 적대적 파일 변경 경쟁이나 업로드 서버의 격리까지 구현하지 않는다.
출처 메타데이터가 있다고 모델 답변이 그 출처에 충실하다는 뜻도 아니다. 실제 출력은 별도 검토한다.

```sh
uv run --locked pytest -q
uv run --locked ruff check .
```
