# Olist RDF/OWL 근거 검증

## 문제와 범위

같은 숫자라도 출처·집계 단위·관측 범위가 다르면 같은 지표로 해석할 수 없다.
특히 계약 판매자가 커머스 표본에 없다는 이유로 판매 0건을 추론하면 안 된다.
기존 PostgreSQL 수치 검증에 더해, 조사 결과와 지표 정의의 의미 관계를 검사한다.

흐름은 `고정된 읽기 스냅샷 → 근거 ID·버전 검증 → RDF 투영 → OWL 2 RL 추론 →
SHACL 검증 → 기존 결과 렌더링`이다. `intent-v1`의 일반 실행과 영속 실행이 같은
렌더 경계를 사용한다. 고정 `action-v5` 기준선에는 적용하지 않는다.

## 경계와 선택

- 숫자·분모는 기존 SQL이 계산한다. RDF는 집계 저장소를 대체하지 않는다.
- 모델이 RDF·SPARQL·SQL·검증 규칙을 생성하지 않는다. 원격 모델 호출을 추가하지 않는다.
- 지표 정의와 선언된 출처 의존성을 RDF로 표현한다. Observation→MetricDefinition→DeclaredSource의
  `derivedFrom` 관계를 OWL의 transitive property로 확장하고, 계층·역관계도 추론한다.
  Evidence→DatasetVersion은 조회 문맥, DatasetVersion→releaseContainsSource는 게시 버전의
  소속 관계다. 이 두 관계를 개별 지표의 출처라고 추론하지 않는다.
- 출처 선언은 검토한 변환 코드 지문에 결합한다. 게시 근거의 transform_sha256이 일치해야 한다.
  리드·계약·유입 누락은 marketing, 판매자 연결 여부는 marketing과 commerce를 의존성으로 선언한다.
  선언된 의존성의 구조 검증이며 개별 원본 행의 런타임 lineage를 입증한 것은 아니다.
- SHACL은 필수 근거 참조, 지표, 단위, 음수·자료형, 데이터 버전의 일관성을 검사한다.
  이어서 Python 검사가 추론된 지표별 출처 경로와 허용된 출처 집합을 확인한다.
- OWL의 추론과 SHACL의 제약 검증을 구분한다. 정보 부재는 판매 없음이라는 사실이 아니다.
- API에는 검증 요약과 근거 경로만 추가한다. 원본 행·DB 연결 정보는 포함하지 않는다.
- 클래스·규칙·지표 정책은 해시 manifest로 고정한다. 파일이 누락되거나 지문이 다르면
  결과를 보류한다. 체크포인트의 소스 결합에도 해당 파일을 포함한다.
- 검증 실패는 `semantic_validation_failed`로 보류하며 결과·판단을 내보내지 않는다.
  기존 게시 데이터와 호출 기록을 수정하지 않는다.
- 읽기 스냅샷에서 만든 작은 요청별 그래프다. 별도 그래프 DB·공유 캐시·게시 포인터를
  추가하지 않으므로 SQL 버전과 그래프 버전의 비동기 갱신 문제를 만들지 않는다.

## 완료 기준

1. 클래스 계층·역관계·출처 관계의 실제 OWL 추론을 확인한다.
2. 필수 속성 누락·자료형·단위·음수·버전 불일치가 실제 SHACL에서 실패하고,
   선언된 출처 경로의 불일치는 후속 Python 검사에서 실패한다.
3. 근거 내용의 지문 변조·다른 버전·지표 정책 변조가 거절된다.
4. 같은 근거 입력은 트리플 삽입 순서에 무관하게 같은 그래프 지문을 만든다.
   SQL 행 순서를 바꿔 근거 ID가 달라졌다면 같은 입력으로 취급하지 않는다.
5. 미관측 주문을 0으로 만드는 추론이 없고, 같은 의미 구분을 API 결과에서 확인한다.
6. 일반·영속 조사에서 검증 실패가 차단되고 재시작 재생은 기존 결과를 보존한다.
7. 기존 회귀 검사·Ruff와 가능한 실제 PostgreSQL/HTTP 경계를 확인한다.

## 운영 한계

신뢰하는 로컬 Turtle 파일만 파싱한다. 원격 imports·JSON-LD context·JavaScript·SHACL rules는
실행하지 않는다. 근거 크기·도구 수·그래프 크기를 제한한다. OWL/SHACL은 동기 CPU 작업이며
서비스의 기존 별도 워커·전체 제한 시간 안에서 실행한다. 이 검증은 출처 값 자체의 진실이나
모델의 일반 답변 정확도를 보증하지 않는다. 고정 스키마가 수치·용어를 일관되게 연결했는지를 검사한다.
검증 앞뒤의 deadline 검사는 CPU 추론을 중간에 끊지는 않는다. 전체 강제 시간 제한은 기존
서비스 워커 감독 경계에서 담당한다. CLI의 timeout은 동기 검증 완료 후 초과를 감지하는 제한이다.

전체 Olist 집계 질문에는 SQL만으로도 답할 수 있다. 이번 확장의 가치는 서로 다른 도구가
내보낸 근거·지표 정의·버전을 같은 의미 계약으로 검사하고, 모델이 아니라 코드가 만든
출처 경로를 제공하는 것이다. 자동 Knowledge Extraction·GraphRAG·장기 기억 구현은 아니다.

## 실행

프로젝트의 Docker PostgreSQL과 읽기 전용 계정을 준비한 뒤 다음을 실행한다. 모델 키는 필요 없다.

```sh
uv run --locked python -m llm_ops_lab.olist.semantics --root . \
  --output runs/olist/semantic-validation.json
```

저장된 근거 JSON 배열은 `--root .` 대신 `--bundle <로컬파일>`로 검사한다. 보고서는 임시 파일의
fsync 후 원자 교체한다. 정상은 종료 코드 0, 검증 실패는 2다. 일반 `intent-v1` 조사 API에도
`semantic_validation` 필드가 추가되며, 실제 모델의 답변 정확도와는 별도의 검증이다.
반환값의 `declared_source_paths_validated`는 변환 코드와 결합한 출처 선언의 경로 검사다.
`row_level_provenance_verified`는 false로 유지한다. count 근거가 없는 품질·실행 이력 질문은
`validation_scope=evidence_structure_only`, 경로 검사는 false로 반환해 숫자 검증으로 오해하지 않게 한다.

`olist-durable.v2`는 의미 계약 파일과 정책·코드의 지문을 실행 결합에 포함한다. 기존 v1 실행 키는
새 코드에서 재사용하지 않는다. 409 source mismatch가 나면 과거 기록을 보존하고 새 요청 키를
사용한다. 기존 호출 예산·원장을 초기화하는 마이그레이션은 수행하지 않는다.
