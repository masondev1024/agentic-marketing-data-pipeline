# 첫 실습: 입력이 답변이 되는 과정

## 먼저 이해할 것

LLM은 입력을 토큰 ID로 바꾸고, 그 문맥 다음에 올 토큰의 점수를 계산합니다.
생성 설정에 따라 토큰을 선택하고 문맥에 붙이는 과정을 종료 토큰이나 출력 한도까지 반복합니다.
이 실습은 이미 학습된 모델을 사용하는 **추론**이며 모델 가중치를 갱신하지 않습니다.

`apply_chat_template`은 사용자 메시지를 모델이 기대하는 대화 형식으로 변환합니다.
`stream_generate`는 다음 토큰 생성 결과를 순차적으로 전달합니다.
`temperature=0`에서는 가장 높은 점수의 토큰을 선택하는 경로를 사용합니다.
temperature를 높이는 것은 정답률을 올리는 설정이 아닙니다.

## 실행

프로젝트 루트에서 아래 명령을 실행하세요. 설치가 끝난 환경에서는 sync를 반복할 필요가 없습니다.

```sh
sh scripts/bootstrap.sh
uv run --locked llm-lab --offline --prompt '데이터 파이프라인에서 멱등성이 필요한 이유를 두 문장으로 설명해 줘.' --temperature 0 --max-tokens 128
uv run --locked llm-lab --offline --prompt '데이터 파이프라인에서 멱등성이 필요한 이유를 두 문장으로 설명해 줘.' --temperature 0.8 --max-tokens 128
```

캐시가 없는 새 환경이라면 첫 실행에서만 `--offline`을 빼세요.
`llm_ops_lab` 모듈을 못 찾는 오류가 나면 [환경 복구 안내](../README.md)를 먼저 확인하세요.
문장 전체가 토큰 하나인 것은 아닙니다. 동일 입력이라면 위 두 실행의 입력 토큰 수가 같아야 합니다.
출력 한도에서는 문장이 도중에 끝날 수 있습니다. 이것을 모델의 완결된 답변으로 평가하면 안 됩니다.
실제 두 번째 실행에서 128토큰 잘림을 확인했으므로, 32토큰으로 줄이는 비교는 선택 실습으로 변경합니다.

세 번째 실습은 첫 temperature=0 실행과 비교합니다. 설정을 그대로 두고 참고 문맥만 추가합니다.

```sh
uv run --locked llm-lab --offline --temperature 0 --max-tokens 128 --seed 42 \
  --prompt '참고: 멱등성은 같은 작업을 여러 번 수행해도 최종 효과가 한 번 수행한 것과 같은 성질이다. 데이터 파이프라인에서는 장애 후 재시도나 중복 이벤트 때문에 같은 데이터가 여러 번 처리될 수 있다. 멱등한 처리는 이때 결과가 중복 반영되는 것을 방지한다.
질문: 데이터 파이프라인에서 멱등성이 필요한 이유를 두 문장으로 설명해 줘.
참고 내용에 근거해서 답해 줘.'
```

이 작업은 입력에 참고 문맥을 직접 제공하는 실습이다. 모델 가중치를 갱신하지 않으며,
문서를 검색하는 단계도 아직 없어 RAG 구현 완료로 부르지 않는다.

## 결과 해석

`runs/`의 JSON에 질문·답변·설정·모델 revision·실행자가 함께 기록됩니다.

- `prompt_tokens`: 대화 템플릿까지 포함한 입력 토큰 수.
- `generation_tokens`: 생성 토큰 수. 보이는 글자 수와 다름.
- `load_seconds`: 다운로드/캐시 확인과 모델 로딩; 온라인 요청 지연과 분리.
- `generation_seconds`: 이 CLI의 전체 생성 시간. 사용자 화면/네트워크 지연은 포함하지 않음.
- `first_generation_event_seconds`: 첫 생성 이벤트까지 시간. 빈 텍스트/특수 토큰일 수 있어
  첫 화면 글자 도착 시간과 같다고 단정하지 않음.
- `mlx_peak_memory_gb`: MLX가 보고한 메모리 최고치; 시스템 전체 RAM이나 프로세스 RSS가 아님.
- `max_tokens_reached`: 출력 한도에 도달했는지. 잘림 가능성을 사람이 확인.

seed와 revision을 고정해도 장비·라이브러리가 달라지면 동일 출력이 보장되지는 않습니다.
3회 실험은 설정 영향 탐색이며 정확도나 성능 개선을 증명하는 통계 실험은 아닙니다.

## 직접 남길 기록

아래 질문에 1~2문장씩 답해서 채팅에 보내거나 별도 학습 기록에 남기세요.

1. 답변에 틀리거나 애매한 내용이 있나요? 멱등성과 중복 방지를 어떻게 설명했나요?
2. temperature만 바꿨을 때 무엇이 달라졌나요? 같았다면 그것도 관찰 결과입니다.
3. 출력 한도에 도달했을 때 답변이 완성됐나요? 참고 문맥을 추가한 세 번째 답변은 핵심을 설명하나요?
4. 실행 중 모델이 새 지식을 학습했나요? 그렇게 판단한 이유는 무엇인가요?

## 직접 코드 수정: system 메시지와 실험 재현

출력 한도를 256으로 늘린 학습자 실험에서 잘림은 해소됐지만 의미·형식 오류는 남았습니다.
이 실행을 다음 비교의 기준선으로 사용합니다.

`src/llm_ops_lab/cli.py`의 `messages` 정의를 다음처럼 수정하세요.

```python
    messages = [
        {
            "role": "system",
            "content": (
                "제공된 참고 내용에 근거해서 답하세요. "
                "제목, 번호, 목록 없이 정확히 두 문장으로 답하세요. "
                "참고 내용이 부족하면 정보가 부족하다고 말하세요."
            ),
        },
        {"role": "user", "content": args.prompt},
    ]
```

같은 함수의 결과 딕셔너리에서 `"input": args.prompt,` 다음에 `"messages": messages,`를 추가하세요.
입력 질문만 저장하면 system 지시가 바뀐 실험을 재현하기 어렵습니다. 기존 필드는 유지합니다.
기존 기록에는 messages가 없으므로 향후 읽는 코드는 이 필드가 없는 v1 기록도 처리해야 합니다.

`uv run --locked pytest -q`와 `uv run --locked ruff check .`를 실행한 뒤,
방금 사용한 문맥 포함 질문·temperature=0·max_tokens=256·seed=42 명령을 다시 실행하세요.
새 JSON에 두 역할의 messages가 기록됐는지, 입력 토큰 수와 답변 형식이 어떻게 달라졌는지 확인합니다.
테스트 통과만으로 모델의 system 지시 준수나 답변 정확도를 확인했다고 판단하지 않습니다.

다음 리뷰 때 변경 코드와 실험 JSON을 봅니다. system 메시지는 추론 입력이며 가중치를 갱신하지 않습니다.
왜 이를 파인튜닝이라고 부르면 안 되는지 본인의 말로 설명해 보세요.
